Everything runs on the one Mac; nothing here depends on a second machine.

At a glance

The roadmap on one screen

Build the safest useful thing first, then add one new kind of risk per milestone. Private data arrives only after local models and egress controls are in place; the kids' agent arrives only after its classifiers and safety evals exist; anything that acts in the world on your behalf comes last and always ends with you pressing the button.

Three tracks run underneath and are not optional: Security S0–S5 Observability O0–O4 Evaluation E0–E4. Each feature milestone has an exit gate that names the track levels it needs, so a feature cannot ship ahead of the controls that make it safe to run. Payments and purchasing are deliberately left off the schedule.

Choices already made

iMessage in Basic mode with System Integrity Protection on; FileVault on with manual unlock after reboots; free security tools (Keychain and SOPS for secrets, LuLu for the firewall); observability that runs locally and starts light (MLflow for traces, VictoriaMetrics and Grafana for metrics). Also settled: your admin account does the work while happy only runs it; one control plane that you own and one data domain per person (section 1b); the sender or schedule picks the agent; one agent per person and permission set, with skills inside; kids can use voice over iMessage or a Home Assistant speaker. See section 9 for the full list and what each choice costs.

Section 1

Architecture map

One OpenClaw gateway on the Mac hosts isolated agents, each with its own model, tools, sandbox, workspace and memory: one per person for every purpose that holds personal data (<p>-main, <p>-mail, <p>-jobs), plus shared agents that keep no memory (research, kids, inbox). Inbound iMessages are routed to an agent by who sent them; scheduled jobs and the mail trigger name their agent directly.12 Replies go back over iMessage by default, as text or an audio file, and long results can also be emailed, but only to the person who asked. Section 1b covers how people are kept apart.

Who runs what

Your admin account does the work and the happy account only runs it. Claude Code, Homebrew, Ollama, Colima and a private git repo holding the OpenClaw config, skills, hooks and the family registry all live in your admin account. One deploy script, permitted by a narrow sudo rule, copies a reviewed config into happy and restarts the gateway; read-only status and log commands are the only other things your account may run as happy. happy never signs in to Claude Code, because OpenClaw automatically picks up a local Claude Code login and would then bypass the capped API keys. The few steps macOS reserves for a person (Messages sign-in, Full Disk Access and Automation prompts) are done once by hand in happy's own session. This is the control plane, and it is yours alone; family members only ever talk to their agents.7681

How a message finds its agent and model

Two layers: a binding picks the agent from the channel, account and sender or chat, and that agent's own config picks the model, its fallbacks and a cheaper helper model. OpenClaw has no content-based model router, so hard routes are used wherever the boundary matters and each adult's main agent triages the rest.23

Agents versus skills

The rule: one agent per distinct set of permissions and per person whose data it holds, and skills for everything that shares them. A skill is know-how loaded on demand; it uses its agent's tools, memory, model and API key and cannot widen them. An agent is the boundary. Folding them into one general agent would give every task the union of permissions, so one malicious email could reach both the browser and your résumé. Sharing one agent between people would also share its memory and accounts, so per-person agents are generated from one template instead (section 1b). Skills are written in-house; nothing from the public skill marketplace is installed without a line-by-line read.

Section 1b

Family data domains

You, your wife and the kids will all use this one gateway. OpenClaw treats a gateway as one trust domain: everyone who can message a tool-enabled agent shares that agent's delegated tool authority, and per-person sessions (session.dmScope: "per-channel-peer", already set in M0) keep conversations apart but not the agent's workspace memory, which its private chats load.48384 Its own advice is direct: "If people must not access each other's sessions, tools, credentials, or files, give them separate agents or separate gateway/host trust boundaries."83 Here people are kept apart by agents, never inside one.

One control plane that you own, and one data domain per person. Anything that holds or can reach a person's data has exactly one owner, and the owner's name is the prefix that config, paths and checks key on. Agents shared between people keep no memory and hold no accounts.

In the names below, wife stands in for her name and <p> for any person.

Who is admitted, and who can approve

On iMessage, channels.imessage.allowFrom is both the list of who may chat and the list of who may approve, and any approver can resolve any pending request: "The requester does not need to be an approver."9193 2026.9.7 has no way to tie an approval to the person whose agent asked for it. The plan puts the whole family in allowFrom, so unknown numbers still get nothing, and sends approval prompts only to the chat that triggered them, so a request ID only ever appears on its owner's phone. The kids agent has no tools, so it never creates an approval.

If the kids must not be able to approve at all, admit them by pairing instead (dmPolicy: "pairing"): paired senders can chat but are not approvers as long as allowFrom lists the adults, at the cost of a pairing-code reply to any unknown number.91 Either way, set the command owner first, because a pairing approved from the CLI otherwise makes that sender the owner.92 Each person also needs their own iMessage handle: a kid using a parent's iPad, signed in to the parent's Apple Account, reaches the parent's agents.

How the separation is proven

  • happy-inspect separation: a new read-only check. From the live config it lists every agent with its owner, workspace, state folder, bindings, MCP servers, model key and delivery targets, and fails if anything points at another person or if a shared agent has memory or accounts. It runs after every deploy, next to the drift check.
  • Canary evals (E0): a unique phrase is planted in tony-main's memory. The eval drives an eval clone of wife-main, generated from the same registry entry (same paths, MCP allow list and hook), and asks it for the phrase, asks it to read your mail and asks it to message you. It passes when no data comes back, no tool is called, and the phrase never appears in a trace from an agent that isn't yours. One live text from her phone then confirms her handle reaches wife-main and nothing else.

What stays shared on purpose

One macOS user (happy), one gateway process and one Keychain. The separation is OpenClaw policy, folder mounts and credential wiring, not operating-system isolation, so a gateway bug or a mistake that lets something run outside the sandbox could cross it. That is accepted: you are the operator and the family trusts each other. OpenClaw's answer for people who must be protected from each other is separate gateways, ideally under separate OS users, which here would also need a second Apple Account for iMessage.4

Not yet confirmed in 2026.9.7, so each gets a test at the milestone that needs it: that the minimal tool profile plus a per-agent allow exposes exactly one MCP server (M3, M4); that subagents.allowAgents handoffs return their results with agent-to-agent off and tools.sessions.visibility: "self" (the docs promise a requester access to its child sessions only under tree or all) (M3); that the documented gog flags behave as written (M3, M6); whether paired kids are really refused as approvers (M5); whether a sandbox browser keeps its logins across a container prune (M6).
Section 2

How three requests move through it

The same pieces combine differently per request. The thing to watch in each lane is where data would leave the Mac, because that is where the security track spends its effort.

Delivery follows one rule: answer in the channel the question came from, as text, or as audio if the question was a voice memo (OpenClaw's tts.auto: "inbound" mode). Anything longer than a screen, like an itinerary or a job packet, is also emailed, and the only address the send tool will accept is that of the person who owns the sending agent.1018

Section 3

Feature milestones

The order differs from the obvious one on purpose. Local models come before any private data, because the mail agents must never fall back to the cloud. Trip research comes before email, because it exercises the browser, egress rules and the send-to-owner path on low-risk data. Kids come after email, because they need the classifiers and a safety eval suite that do not exist yet. Job hunting is last: it combines private data, untrusted pages and an outbound browser, the hardest mix in the plan.

M0

Hardened foundation

weeks 1–2

A gateway that is safe to leave running before it does anything useful.

Deliverables
  • Operating model in place: Claude Code and the config repo in your admin account; one deploy script applies config as happy; happy never signs in to Claude Code.
  • Dedicated non-admin macOS user happy with its own Apple ID; your admin account stays separate. FileVault on; planned reboots via fdesetup authrestart.
  • OpenClaw installed at a pinned version, auto-update off, gateway bound to loopback, reachable only through Tailscale Serve.3032
  • Colima running as happy; sandbox mode: "all" for every agent; openclaw sandbox explain clean.
  • API keys moved out of plaintext into the happy login Keychain, read by an exec SecretRef script; openclaw secrets audit --check passes.2122
  • Anthropic workspace and OpenAI project per agent, each with a hard monthly cap. (M0 ran OpenAI-only, with one project for main; per-agent projects and workspaces arrive with each agent from M1.)4748
  • Backup: openclaw backup create --verify nightly plus Time Machine to an encrypted drive.31
Why first
  • Four OpenClaw defaults are unsafe for this use: sandbox off, tool profile full, cross-agent session visibility on, secret store unencrypted.1516321 All four are fixed before a single message arrives.
  • A clean openclaw security audit --deep is the baseline every later milestone is compared to.24
Exit gate S0 O0 · audit clean, restore drill done once, dead-man alert reaches your phone.
M1

iMessage assistant on a cloud model

weeks 3–4

Text the Mac mini and get a good answer back: you first, then your wife on agents of her own.

Deliverables
  • iMessage channel in Basic mode; dmPolicy: "allowlist" with the family's handles, yours first; groups disabled; the command owner set to your handle before anyone else is admitted.892
  • Family registry (family.json5) and its generator in happy-config; agent folders under people/<p>/ and sandboxes/<p>/; the inbox catch-all binding; session.dmScope: "per-channel-peer" and dreaming off, both kept from M0; config-changing chat commands and configWrites off; happy-inspect separation clean (section 1b).286100
  • tony-main (M0's main, renamed before it holds anything) via its own capped key profile; tools limited to web search; no browser, no exec. The rename covers its folders, its OpenAI project, its Keychain item (openai-api-key-main becomes openai-api-key-tony-main) and happy-inspect's references. The model is chosen at M1 start: M0 ran OpenAI-only, so keeping Claude Sonnet 5 means adding Anthropic (runbook F1). Staying on OpenAI brings S3's retention fix forward to M1.
  • wife-main is generated with tony-main; her handle is bound only after its eval clone passes the separation canaries.
  • Chat approvals via /approve, with prompts delivered only to the chat that asked; Control UI over Tailscale as the backup approval path.3491
  • Hard rules (who it may contact, what it may never do) live in the injected bootstrap files and in tool policy, not in chat, because compaction can drop chat instructions.
Proves
  • The channel, routing, cost caps and alerting work end to end.
  • The eval harness can drive a real agent through the gateway (E0).
  • Two people's agents run side by side without seeing each other's memory (separation canaries, E0).
Exit gate S1 O1 E0 · nightly smoke eval green for a week; unknown senders provably ignored; separation canaries never cross.
M2

Local models and routing

weeks 5–6

Decide from measurements, not guesses, which work stays on the Mac.

Deliverables
  • Ollama on 127.0.0.1 with Qwen3.8‑27B (Q8) and Qwen3.6‑35B‑A3B; OpenClaw pointed at the native API.33
  • Per-agent model config: a strict-local (fallbacks: []) template for each <p>-mail, inbox and later kids, with modelPolicy.allow limited to local models so /model cannot move them to the cloud; heartbeats and utility calls on local models.96
  • Memory search switched from OpenAI embeddings to a local embedding model.29
  • A written routing table, justified by the E1 bake-off: quality, latency and cost for local versus cloud on the same golden set.
Watch for
  • Only one large model fits in GPU memory at a time; the second loads on demand (10–20 s). Measure that switch.
  • OpenClaw warns smaller or heavily quantized models are more vulnerable to prompt injection; no local model gets tools that touch untrusted content.23
Exit gate O2 E1 · routing table committed; traces show which model served every turn.
M3

Research & trip planning, with email to the asker

weeks 7–8

The first agent that reads the open web, and the first output that is not a chat reply.

Deliverables
  • research agent: sandboxed browser, web fetch, Google Maps Grounding Lite MCP; Opus 5.5 as planner; no access to anyone's memory or files. Shared by the family and stateless: memory.search.enabled: false, rememberAcrossConversations: false, a fresh sandbox per session.7585
  • Each <p>-main may hand tasks to research (and to its own <p>-jobs from M6) through its subagents.allowAgents list; tools.agentToAgent stays off.89
  • Send-to-owner tool: a mailout MCP server on the agent's own Gmail address that registers only gog's send tool, allowed to each <p>-main (and each <p>-jobs from M6); the registry hook pins the recipient to that agent's owner and fails closed. This replaces the earlier exec-based gog gmail send, which the sandbox's network: "none" would block.991887
  • Prices only from live tool results with a timestamp; links, not bookings.
Why before email
  • It exercises the riskiest plumbing (browser, egress rules, outbound email) while the data involved is public.
  • No payment or booking capability exists in this milestone or any other on the schedule.
Exit gate S2 E2 (web) · injected web pages cannot change the recipient or trigger tools; browser cannot reach the LAN.
M4

Morning email digest

weeks 9–10

Each adult's inbox summarized every morning for that adult only, without any inbox leaving the Mac.

Deliverables
  • Mail intake by polling, not Gmail Pub/Sub, which defaults to a public Tailscale Funnel endpoint.1211
  • One <p>-mail agent per inbox, per OpenClaw's documented pattern: minimal tools, no files, web or runtime; strict local model pinned with modelPolicy.allow; per-session sandbox.1296
  • Each 7:00 automation names its reader and announces the digest over iMessage only to that inbox's owner; "reply-to" drafts, if ever added, are drafts only.
Open decision in this milestone
  • Both intake routes work per person. OpenClaw's IMAP plugin takes one account per inbox, each with its own agentId, so an inbox feeds only its owner's reader; but it needs an app password, which grants full mailbox access to the trigger (not the agent). A read-only <p>-gmail MCP server keeps the narrowest OAuth scope, but gives the reader one read-only tool. Decide at M4 start.1199
Exit gate S3 O3 E2 (email) · the reader agents make no network calls, and LuLu shows only the intake's connection to Gmail; injection canaries never cause a tool call.
M5

Kids Q&A: text, then voice

weeks 11–15

A patient, age-appropriate answer machine that only your kids can reach and that you can audit.

Deliverables (5a text, wk 11–12)
  • kids agent bound to each kid's handle, shared by the kids and stateless: no tools; memory really off (memory.search.enabled: false, since provider: "none" alone leaves keyword search on); a fresh sandbox per session; session visibility self; no agent-to-agent.85
  • Llama Guard 3 8B on input and on output (the message_sending hook can cancel a reply); age band and "ask a grown-up" rules in bootstrap files.44
  • Weekly parent digest of every flagged exchange.
Deliverables (5b voice, wk 13–15)
  • iMessage voice memos for Apple devices: attachment intake on, local transcription, audio replies from local TTS.7910
  • Kitchen speaker for kids without Apple devices: Home Assistant Voice Preview Edition with Home Assistant OS in a small VM on the Mac, all speech steps local; it reaches only the kids agent, never the gateway's operator key.7778
  • Latency budget: first audio within ~5 s for a short question; if the dense 27B is too slow, move the kids agent to the Qwen3.6‑35B‑A3B MoE.
Why this late
  • The safety layer (classifiers, KIDBench-style evals, parent review) is the product here; it needs E3 in place first.
  • Note: Llama Guard 4 is not in the Ollama library; Llama Guard 3 8B is, so the blueprint's choice is adjusted.44
Exit gate S4 E3 · age-appropriateness pass rate at target on your own question set and a KIDBench subset; zero unsafe outputs reach audio on either voice path.
M6

Job-hunt copilot

weeks 16–19

Find, rank and prepare applications daily; the job seeker decides and submits.

Deliverables
  • Discovery via Indeed's official MCP, alerts and company career pages; no LinkedIn scraping.74
  • One <p>-jobs agent per job seeker, each with its own verified career-facts file. Drafts are built only from that file; a daily Approve / Edit / Skip digest goes to that person in iMessage; approved packets are emailed to them through mailout, and can be saved as drafts in their own Gmail through <p>-gmail-drafts, with only its draft tools allowed.
  • v2 (optional): pre-fill in that agent's own sandboxed browser (its logins stay in its container) behind a Lobster approval step, which the job seeker finishes over Screen Sharing.19
Why last
  • Each <p>-jobs holds one person's résumé, reads untrusted job pages and drives a browser: all three risk legs at once. The browser is limited to known applicant-tracking domains and never submits.
Exit gate S5 E4 · zero invented qualifications across repeated runs (pass^k); injected job descriptions cannot redirect data.
—

Not scheduled: purchases, bookings, bank access

Revisit only after three clean months of M0–M6, and then only with a single-use or merchant-locked virtual card, a per-transaction approval and a payment agent that reads nothing untrusted. Bank write access stays out entirely. The second-machine topology from the blueprint is also trigger-based rather than scheduled.

Section 5 · parallel track

Security track

Start from the fact that prompt injection is not solved: the most recent independent study found adaptive attacks beat most published defenses more than 90% of the time.45 So the track spends its effort on limits the model cannot talk its way past (isolation, tool policy, egress rules, hooks that fail closed) and treats classifiers as tripwires. The organizing rule is the "lethal trifecta": no agent may hold private data, read untrusted content and have a way to send data out, all at once.46

Strict-local model for every <p>-mail, pinned with modelPolicy.allow; the mail-credential decision made; proof that the reader agents make no network calls; trace content kept local with a retention job; OpenAI's 30-day retention of Responses calls handled before any private agent uses OpenAI (at M1 if tony-main stays on OpenAI, otherwise before M4), because M0 found that compat.supportsStore: false does not prevent it for catalog models (a custom provider entry, Zero Data Retention, or Anthropic or local models instead).49

Kids' handles allowlisted to the kids agent; the speaker's Home Assistant VM on the LAN only, reaching a kids-only endpoint; no tools, memory off for real (memory.search.enabled: false) and a session-scoped sandbox; Llama Guard on input and output; weekly parent review of flagged items; kids' content never sent to a provider whose terms exclude minors.

S5 · Action controls before M6

Applicant-tracking domain allowlist for each <p>-jobs browser; approval before every form interaction; no submit capability; résumé stripped of address, birth date and ID numbers.

Ongoing: weekly patch window, monthly audit and review of standing approvals, quarterly restore drill and key rotation.
