The jobs script. If step C2 shows that the deploy path reaches the scheduler, Claude runs sudo -n -u happy /usr/local/libexec/happy-deploy --jobs <command>. If it does not, you run ~/bin/happy-jobs <command> in happy's Terminal and tell Claude the lines it prints. happy-gog

Screen on happy
The Mac's screen shows happy's desktop, reached by fast user switching. The test is that stat -f %Su /dev/console prints happy (the firewall view of happy-inspect shows it); reaching happy's desktop some other way does not count unless that line says happy. LuLu's firewall rule for the connector is enforced only in this state; the proxy, which is the connector's main limit, works in every state (see "Where the research changed the plan"). While the screen is on happy you cannot talk to Claude, so the steps say what you run there yourself and what Claude reads afterwards.

Where the research changed the plan

  • The "one firewall rule" cannot name Google's hosts. LuLu can match a host name only when macOS supplies one, which it does for connections made through its name-based APIs. gog is a Go program and connects to numeric addresses, so a rule such as "gog may reach gmail.googleapis.com" would never match. The gate is therefore built in two parts: one LuLu rule that blocks everything gog tries directly, and a local proxy, the only thing gog is ever pointed at, that opens tunnels to three named Google hosts and refuses the rest. The proxy keeps a log by host name, which is better evidence than LuLu could give. It is a component the catalog did not have, and it needs your yes at A4.
  • LuLu's rule holds only while happy's desktop is on the screen. LuLu serves one console user: it records who owns the screen when its app connects, and while another user owns it, it allows everything, block rules included. Its author says multi-user support is "not supported at all" for now. So LuLu's app lives in happy's session and is never opened in the admin account, D1 measures the screen states, and steps that touch real mail are run with the screen on happy. The proxy does not have this weakness, which is why it is the main limit and the LuLu rule the backstop.
  • A helper can never hold a tool its asker lacks. On 2026.9.7 an agent started by another through sessions_spawn keeps only the tools its asker is allowed. The docs call this "inherited tool policy"; the installed code shows how: the asker's list of allowed tools and its denies are stored on the helper's session and applied as the last filter, also when the helper is a different agent with a tool list of its own. No setting turns it off. The catalog's first lookup design, in which your own agent denies the Gmail tools and the reader it starts still reads mail, therefore cannot work. On 13 Oct you chose the shape that can: your own agent is allowed the reader's three tools, hands the work over and is told never to use them itself. Phase H builds and tests that. What keeps your agent to its rule is an instruction, checked by its tool-call record, and no longer a tool limit.
  • The scheduler is not empty, and a job without a tool list is not harmless. OpenClaw keeps a system-owned weekly review job per agent unless skills.workshop.autonomous.mode is off; B3 switches it off. A job created without --tools gets the cap "any tool", and a turn whose explicit tool list leaves nothing callable is refused, so the throwaway probe on the tool-less inbox agent passes --tools "".
  • gog keeps the sign-in client's secret in the keyring too, and its Keychain entries share one name whatever folder it runs in. Hence the wrapper bin/happy-gog, which gives each sign-in its own Keychain namespace and folder, points gog at the proxy, and is the only way anything starts gog.
  • gog's exit status does not show a broken sign-in, and in a Terminal it offers to repair one. Upstream says auth list --check can exit 0 with an unhealthy token, so the daily check reads each entry's valid field. Without --no-input gog asks whether to re-authorize a dead token, and a yes would replace the token that test T1 is measuring; every scripted call here passes --no-input.
  • A read-only grant still shows gog's draft and label tools. The connector is started with three exact tool names (gmail_search, gmail_get_message, gmail_get_thread), so your drafts are not readable either.
  • A hand-off's time limit cannot be set per agent. 2026.9.7 rejects subagents.runTimeoutSeconds under an agent (config validation, tried on a scratch copy), so the two-minute limit is the gateway-wide default.
  • Re-adding a job under the same key updates it. That is what the installed scheduler code does (dist/service-*.mjs, add()), and the CLI leaves a re-declared job's on/off state alone unless --disabled is passed. C3 still proves it live, as the catalog's test T3 asks.
  • The reader's records are not "deleted after 30 days". OpenClaw keeps the latest run's transcript of a scheduled job for as long as the job exists, earlier ones until its disk budget evicts them, and each run's history row, with the text, for 7 days. The texts themselves stay in Messages on both ends. The jobs script keeps nothing from a run over real mail. With the lookup on, each mail question also leaves the reader's transcript of that hand-off, archived an hour after it finishes and kept until the disk budget evicts it. Nothing else is changed here; the optional settings are your call at A4, and what is kept is on the sign-off page.
