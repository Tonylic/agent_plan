Operations

After wave A

The connector's two limits, day to day

  • The proxy is the main limit and needs nothing from you: it runs as a LaunchAgent in happy's session (restarted if it stops), and gog can reach the internet only through it. sudo -n -u happy /usr/local/libexec/happy-inspect egress shows what it let through and what it refused, by host name. If it is down, mail fails closed: gog reaches nothing. The 06:30 sign-in check alerts you the same morning ("Google sign-in not working"; the check's own log line, which happy-signin-check prints, says that the proxy is not answering); the job's own alert comes only after a second failed run.
  • The firewall rule behind it holds only in the screen states that D1 recorded as "direct: blocked". So: end every sitting in the admin account by switching the screen back to happy's desktop; never open LuLu in the admin account; never choose Quit LuLu (it switches filtering off). After a restart of the Mac, an upgrade or a relaunch of LuLu, run /usr/local/libexec/happy-inspect fwprobe in happy's Terminal with the screen on happy; it must read "direct: blocked | via proxy: refused, allowed host ok". Whenever LuLu is enabled again, upgraded or relaunched, also restart Colima (launchctl kickstart -k gui/$(id -u)/local.happy.colima in happy's Terminal) and text Happy once: turning LuLu on breaks Colima's connection into its VM, and every Happy turn then fails with "Docker daemon is not available" (seen on 18 Oct; Grafana's "Sandbox runtime down" rule fires too).
  • happy-inspect firewall shows the static state: who owns the screen, LuLu's extension and app, the proxy and its allowed hosts.
  • To allow one more host (only one that ends in .googleapis.com or .google.com, and only when the proxy's record shows gog was refused it): add it to egress/allow-hosts, commit, stage and deploy. The deploy restarts the proxy when its files changed and says so; removing a host works the same way. Until the restart the running proxy keeps the list it started with.
  • The proxy's log (~/Library/Logs/happy/egress-proxy.log) grows by a few lines per run and is not rotated; look at its size in the monthly checklist.

Quieten, change or stop a scheduled text

  • Quieten: JOBS disable mail-morning-tony and JOBS disable mail-morning-tony-mon; JOBS enable … brings each back. Or silence the thread on the phone.
  • Change the wording: edit templates/mail/morning.txt, run node scripts/gen-family.mjs, commit, stage and deploy, wait for the eval run that the deploy starts to pass, then JOBS apply (it updates the jobs in place and leaves each one's on/off state alone). A job keeps the message it was last applied with.
  • The first two weeks: read each morning text against your inbox now and then, and note which school systems actually write to you. Only then change a school platform's own notification settings, and only for one that shows up (catalog card F051).
  • If a run over real mail fails: Claude reads status lines only (JOBS list) and reproduces the fault on the test copy (JOBS run mail-morning-test). Anything that can hold mail text is yours to read, in happy's Terminal: openclaw automations runs <id> --limit 1.
  • Every job: sudo -n -u happy /usr/local/libexec/happy-inspect jobs lists them all, disabled ones included. A job that failed ten times in a row is switched off by OpenClaw and shows as "off"; the cause is in openclaw automations show <id> in happy's Terminal.

The lookup, day to day

  • That your own agent never reads mail itself is an instruction, not a limit, until wave C's coded check (if the catalog's test T5 shows that one can be written). To look at its record: sudo -n -u happy /usr/local/libexec/happy-inspect calls tony-main. It lists tool names for its live sessions only, and a session reset (04:00, or /new) starts the counts again, so it is a spot check and not a log. A name beginning tony-gmail__ there means it read mail itself: switch the lookup off (see "The way back") and tell Claude what you had asked.
  • The lookup can be switched off at any time without touching the morning text.

When "Google sign-in not working" fires

  1. In happy's Terminal run ~/bin/happy-signin-check; it names the sign-in that is not working (it tries a failing one three times, a minute apart, before it says so). If the line says the egress proxy is not answering, the sign-in was not tested: start the proxy (launchctl kickstart -k gui/$(id -u)/local.happy.egress-proxy) and run the check again.
  2. Its owner approves it again: ~/bin/happy-gog <sign-in> auth add <address> --services gmail --gmail-scope readonly --force-consent --manual, with the browser steps of B7. In this wave <sign-in> <address> is tony-gmail redacted-tony-gmail@example.com or test-gmail redacted-test-mailbox@example.com.
  3. Run the check again; the RESOLVED push follows.

Google's listed causes for a token that stops working: the owner removed the app's access; the token went unused for six months; the owner changed their Google password (tokens with Gmail scopes are revoked by that); more than 100 tokens for the same client and account; and a Testing app's seven days.

Upgrading gog or LuLu

  • Homebrew runs only in the admin account. gog and tinyproxy are pinned. To move gog: brew unpin openclaw/tap/gogcli && brew upgrade openclaw/tap/gogcli && brew pin openclaw/tap/gogcli, then repeat B2's checks (all but gog update status, which the firewall rule now blocks), happy-inspect fwprobe with the screen on happy (the rule is keyed to gog's signature, but prove it), ~/bin/happy-signin-check, and an on-demand eval run. The eval fingerprint includes gog's version, so a deploy after the upgrade starts one anyway. To move tinyproxy: unpin, upgrade, pin, restart it (launchctl kickstart -k as above) and run fwprobe.
  • LuLu is pinned too. Upgrade it only in the patch window: Claude runs brew unpin --cask lulu && brew upgrade --cask lulu && brew pin --cask lulu in the admin account; then you switch to happy's desktop, open LuLu there, and D1 and D2 are repeated.

The way back

  • Morning text: JOBS disable both jobs. Nothing else changes.
  • Lookup: lookup: "off" in family.json5, regenerate, commit, deploy with a restart. Your own agent then loses the hand-off and the three Gmail tools again, and denies them by name as before H1.
  • The reader: first JOBS remove the two real jobs (a job whose agent is gone would fail and alert you); then stage: "eval" with lookup: "off" (only the test copy remains), or remove "mail" and the mail block and JOBS remove mail-morning-test as well; regenerate, commit, deploy with a restart.
  • A sign-in: in the Google Account's linked apps remove the app's access (this alone ends the token); on the Mac, ~/bin/happy-gog <sign-in> auth remove <address> --force (the same pairs as above; without --force it asks first), then delete the folder ~/.config/happy/gog/<sign-in> in happy's Terminal, or the daily check keeps reporting it as not working.
  • LuLu: menu-bar icon › Disable switches the filter off at once; Quit LuLu and Uninstall LuLu ask for the admin password, and quitting also switches filtering off. Without LuLu the connector still has the proxy, but nothing stops a gog that ignores it; say so in the log, and disable the two jobs if it is to stay off.
  • The proxy: launchctl bootout gui/$(id -u)/local.happy.egress-proxy in happy's Terminal stops it. gog then reaches nothing, so disable the two jobs first.
